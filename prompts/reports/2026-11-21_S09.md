## Deferred Uncertainties / Design Questions

1. **`SYNC-S09-04` — `admin_app` `media` Channel Authorization & Pruning Coupling (`rust/src/db.rs:679-683, 1516-1547` vs `php/sync.php:876-898, 983-990, 1181-1202`)**
   - **Problem:** PHP `load_channel_members('media')` reads `members.media.php` if present and falls back *only* to `members.card.php` when absent — meaning `backup`/`wot`/`post`-only friends lack `media`, and an explicit `PUT ?members&channel=media` (`[]`) isolates and prunes `media` independently of `card`. Rust instead grants `"media"` to `admin_app` members whenever `allowed.iter().any(|c| c != "lock")` (`has_blob_channel`) and only prunes media when `resolve_member_access_in_txn` returns `None`, so `backup`-only friends receive `media` and explicit `PUT ?members&channel=media` cannot isolate/prune `card` friends' media blobs.
   - **Options:**
     1. Align Rust to PHP (`media` table entry tracked explicitly when set via `PUT ?members&channel=media`, falling back to `card` only while no explicit `media` list exists, plus `media`-scoped pruning parity).
     2. Align PHP to Rust (`has_blob_channel` grants `media` unless explicitly restricted; document in `SPEC.md`).
     3. Keep Rust's `has_blob_channel` intentionally if `human-money-app` relies on `backup`-only friends having `media` access.
   - **Recommendation:** Align Rust and `SPEC.md` to Option 1 for strict PHP↔Rust authorization/pruning parity unless `human-money-app` specifically expects `backup`-only `media` access.

2. **`SYNC-S09-05` — `DELETE ?account` Response Schema & `PUT ?revoke` Normalization/Replay Parity (`php/sync.php:1257-1354, 287-299, 1825-1828` vs `rust/src/sync_routes.rs:458-496, 830-839`, `rust/src/crypto.rs:280-312`)**
   - **Problem:** Two wire/policy mismatches on admin/account JSON endpoints:
     1. `DELETE ?account` returns `"deleted_account": "<64-hex-pubkey>"` (string) in PHP vs `"deleted_account": <bool>` (`+ deleted_slots, deleted_media`) in Rust.
     2. On `PUT ?revoke`, PHP clears on missing/`0` `effective_at`, rejects stale `issued_at <= current` (`409`), rejects self-redirect `replacement` URLs (`400`), enforces HTTPS-or-loopback URLs (`is_sync_url_valid`), and stores lowercase `drop_pub`/`replacement.drop_pub`; Rust clears only on `null`/`clear:true`/`revoked:false`/`effective_at:null`, accepts stale `issued_at`, allows self-redirects and arbitrary `http://` URLs via `is_valid_lock_delegation_url`, and preserves uppercase hex in stored `drop_pub`/`replacement.drop_pub`.
   - **Options:**
     1. Standardize canonical schema in `SPEC.md` (`deleted_account` field semantics; `PUT ?revoke` stale-`issued_at`, self-redirect, and URL scheme rules) and align both PHP and Rust.
     2. Keep `humoco_proto::SyncRevocationNotice::verify` as the permissive baseline and relax PHP to match, while clarifying `DELETE ?account` JSON keys in `SPEC.md`.
   - **Recommendation:** Confirm desired `SPEC.md` contract first (especially whether `deleted_account` breaking wire change in Rust or PHP affects wallet clients, and whether revocation self-redirects / HTTP replacement URLs / stale `issued_at` should be strictly rejected across both runtimes).
